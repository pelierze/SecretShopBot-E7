# 이벤트 자동화 기능 구현 계획

## 1. 목적

에픽세븐 이벤트의 이동을 자동화하는 `이벤트` 탭을 추가한다.

- 사용자가 `100M 플랜`, `200M 플랜`, `300M 플랜` 중 하나를 선택한다.
- 선택한 목표 거리까지의 도달 가능성과 음료수 효율을 높이도록 아이템을 사용한다.
- `350M`에 도달한 뒤에는 남은 아이템을 최대한 사용하여 `400M` 도달을 목표로 한다.
- 이벤트가 종료되면 `이벤트` 탭은 유지하되 자동화 기능은 실행할 수 없도록 정지 상태로 전환한다.
- 현재 프로젝트의 세션 구조를 따라 앱플레이어별 실행 상태, 통계, 로그를 독립적으로 관리한다.

## 2. 현재 확인된 규칙

### 2.1 맵과 보상

- 시작 위치: `0M`
- 한 칸: `10M`
- 핵심 보상 위치: `100M`, `200M`, `300M`, `350M`
- 핵심 보상은 반복 획득할 수 있다.
- 보상 가치는 `100M < 200M < 300M < 350M` 순서다.
- 도움닫기 또는 슈퍼럭키로 보상 위치를 지나쳐도 통과한 모든 핵심 보상을 획득한다.
- 이동 실패 시 위치는 `0M`로 돌아간다.
- 실패 전에 획득한 보상은 보존된다.
- 위치별 이동 성공 확률은 서로 다르며, 확률표는 추후 제공한다.

### 2.2 이동 수단

| 이동 방식 | 음료수 소모 | 아이템 소모 | 성공 판정 | 성공 시 결과 | 실패 시 결과 |
|---|---:|---:|---|---|---|
| 기본 이동 | 1개 | 없음 | 현재 위치 기준 확률 | `+10M` | `0M`로 복귀 |
| 보호 + 기본 이동 | 1개 | 보호 1스택(항상) | 현재 위치 기준 확률 | `+10M`, 보호 1스택 차감 | 제자리 유지, 보호 1스택 차감 |
| 도움닫기 | 1개 | 도움닫기 1스택 | 현재 위치보다 한 칸 뒤의 확률 | 최종 위치 기준 `+30M` | `0M`로 복귀 |
| 슈퍼럭키 | 3개 | 슈퍼럭키 1스택 | 성공 판정 없음 | 무조건 `+30M` | 없음 |

도움닫기는 게임 내부에서 현재 타일의 한 칸 뒤에 서 있는 것으로 판정한 뒤 4칸을 이동하므로, 실제 최종 위치는 현재 위치에서 3칸(`30M`) 전진하는 것으로 해석한다.

### 2.3 아이템 보유 한도

| 아이템 | 시작 스택 | 최대 스택 | 제약 |
|---|---:|---:|---|
| 보호 | 2 | 4 | 다른 아이템과 병행 불가, 기본 이동에만 사용 가능 |
| 도움닫기 | 1 | 2 | 도움닫기에 사용 |
| 슈퍼럭키 | 2 | 2 | 슈퍼럭키에 사용 |

보호는 같은 타일에서 연속 사용할 수 있으며, 보호 실패 후 별도 팝업 없이 보호 재사용·도움닫기·슈퍼럭키 중 하나로 바로 전환할 수 있다.

## 3. 구현 범위

### 3.1 GUI

`src/gui.py`의 세션별 기능 노트북에 네 번째 `이벤트` 탭을 추가한다.

예상 구성:

- 상태: 이벤트 활성/종료, 현재 위치, 음료수, 아이템 스택
- 플랜 선택: `100M 플랜`, `200M 플랜`, `300M 플랜`
- 선택한 플랜의 목적과 아이템 운용 방식을 설명하는 도움말
- 설정: 이미지 매칭 정확도, 동작 간 대기 시간, 안전 중지 조건
- 제어: 이벤트 시작, 중지, 상태 재인식
- 통계: 100/200/300/350M 도달 및 보상 획득 횟수, 이동별 시도/성공/실패, 0M 롤백 횟수, 음료수 및 아이템 사용량
- 공용 세션 로그에 판단 근거와 실행 결과 기록

이벤트 종료 상태에서는 탭과 누적 통계는 보이게 유지하고 시작 버튼 및 실행 설정만 비활성화한다.

#### 앱에 표시할 플랜 설명

| 옵션 | 사용자용 설명 문구 |
|---|---|
| 100M 플랜 | `아이템을 적극적으로 사용해 100M 도달 가능성을 최대한 높입니다. 100M 보상 획득 후에는 남은 아이템을 활용하면서 다음 도전을 준비하고, 0M로 돌아가 100M 보상을 반복해서 노립니다.` |
| 200M 플랜 | `아이템을 적극적으로 사용해 200M 도달 가능성을 최대한 높입니다. 100M와 200M 보상을 획득한 뒤에는 남은 아이템을 활용하면서 다음 도전을 준비하고, 0M로 돌아가 200M 보상을 반복해서 노립니다.` |
| 300M 플랜 | `300M 도전을 위해 앞 구간에서는 아이템과 음료수를 효율적으로 운용하고, 위험한 구간에 아이템을 집중합니다. 300M 이후에는 350M 보상을 거쳐 남은 아이템을 최대한 사용해 400M 도달을 노립니다.` |

플랜은 실행 시작 전에 선택하며 실행 중 변경은 허용하지 않는 것을 기본으로 한다. 변경하려면 현재 실행을 중지한 뒤 새 플랜으로 다시 시작한다.

### 3.2 이벤트 봇

`src/event/events/2026_summer_event/bot.py`에 GUI와 분리된 이벤트 상태 머신을 구현한다. 공통 모델과 화면/입력 인터페이스는 `src/event/`에 두어 이후 이벤트에서도 재사용한다.

주요 상태:

1. 화면 및 이벤트 활성 여부 확인
2. 현재 위치·아이템 스택 인식
3. 현재 목표와 성공 확률에 따라 이동 방식 선택
4. 버튼 실행
5. 성공, 실패, 보호 발동 또는 보상 획득 결과 확인
6. 내부 상태 및 통계 갱신
7. 설정 종료 일시와 중지 조건 확인 후 반복

봇은 게임 결과를 자체 확률로 생성하지 않는다. 제공될 성공 확률은 이동 방식 선택에만 사용하고, 실제 성공/실패는 화면 인식 결과로 확정한다.

### 3.3 정책과 상태 모델

GUI/ADB와 독립적으로 테스트할 수 있도록 다음 데이터를 별도 모델로 둔다.

- `EventState`: 현재 위치, 아이템 스택, 획득 보상, 선택 플랜, 이벤트 활성 상태
- `ShieldAttemptState`: 현재 타일에서 사용한 보호 횟수, 연속 실패 횟수, 해당 타일 보호 사용 한도
- `EventAction`: 기본 이동, 보호 이동, 도움닫기, 슈퍼럭키, 중지
- `EventPolicy`: 현재 상태와 위치별 성공 확률을 입력받아 다음 행동 결정
- `EventStats`: 위치별 도달 횟수, 이동별 결과 및 소비량

정책은 다음 우선순위를 기반으로 하되, 미확정 규칙과 확률표를 받은 후 거리 도달 확률과 음료수당 기대 보상 계산으로 확정한다.

1. 다음 실패 위험, 현재 위치, 선택 플랜과 남은 아이템을 평가한다.
2. 100M 플랜은 100M 도달 확률을 최우선으로 하여 아이템을 적극적으로 사용한다.
3. 200M 플랜은 200M 도달 확률을 최우선으로 하여 아이템을 적극적으로 사용한다.
4. 300M 플랜은 앞 구간에서 아이템을 효율적으로 배분하고 고위험 구간에 집중하여 300M 도달 확률을 높인다.
5. 목표 보상 획득 후에는 남은 아이템을 활용해 추가 보상 또는 다음 고가치 지점 도달을 시도하며, 실패로 0M에 복귀하면 같은 플랜을 반복한다.
6. 300M를 통과한 경우 350M 보상을 목표로 하고, 350M 이후에는 남은 아이템을 최대한 사용해 400M를 목표로 한다.
7. 보호는 성공 여부와 관계없이 스택을 소모하므로 실패 방지 기대효과가 큰 기본 이동 구간에 사용한다.
8. 도움닫기은 한 칸 뒤 확률을 적용했을 때 기본 이동 대비 효율이 높은 구간에 사용한다.
9. 슈퍼럭키는 음료수 3개 비용과 확정 30M 이동으로 통과 가능한 보상 타일의 가치를 함께 평가한다.
10. 안전하게 판단할 수 없는 화면 상태에서는 클릭하지 않고 재인식 후 중지한다.

> 정확한 최적 정책은 성공 확률, 보상별 상대 가치, 아이템 충전 조건이 있어야 계산할 수 있다. 보상 가치의 순서는 확정되었으나 최적화를 위해서는 가능하면 보상별 상대 가중치도 제공받는다.

#### 보호 사용 정책과 실패 후 분기

보호는 한 번의 행동만 선택하는 방식이 아니라, 같은 타일에서 발생할 수 있는 연속 실패까지 포함한 조건부 플랜으로 계산한다. 정책은 타일에 진입할 때 다음 내용을 함께 결정한다.

확정된 보호 연속 사용 규칙:

- 같은 타일에서 보호를 연속으로 사용할 수 있다.
- 보호 실패 직후 도움닫기 또는 슈퍼럭키로 전환할 수 있다.
- 연속 보호 사용 사이에 별도 팝업이나 추가 입력은 없다.

- 해당 타일에서 보호를 최대 몇 회 사용할지(`0~현재 보호 스택`)
- 첫 보호 이동이 실패했을 때 보호를 다시 사용할지
- 보호를 정해진 횟수만큼 사용한 뒤에도 통과하지 못했을 때 선택할 대체 행동
- 보호 스택을 현재 타일에 더 사용할지 이후의 고위험 타일을 위해 보존할지
- 남은 보호 스택이 처음 예상과 달라졌을 때 전체 경로를 다시 계산할지

보호 실패 후에는 성공 확률이 같더라도 상태가 달라진다. 위치는 유지되지만 보호 1개와 음료수 1개가 줄었으므로, 기존 행동을 무조건 반복하지 않고 아래 순서로 정책을 다시 평가한다.

1. 현재 타일의 보호 사용 횟수와 남은 보호 스택을 갱신한다.
2. 선택 플랜의 목표까지 남은 위험 구간과 필요한 보호 예산을 다시 계산한다.
3. 현재 타일에서 보호를 한 번 더 쓸 가치와 이후 타일에 보존할 가치를 비교한다.
4. 보호 재사용, 기본 이동, 도움닫기, 슈퍼럭키 또는 안전 중지 중 후속 행동을 선택한다.

예를 들어 특정 타일의 정책은 다음과 같은 형태로 저장할 수 있다.

```text
90M 진입
├─ 보호 잔여 2개 이상: 보호 이동
│  ├─ 성공: 100M 정책으로 이동
│  └─ 실패: 보호 잔여/후속 위험 재평가
│     ├─ 보호 예산 충족: 보호 이동 1회 재시도
│     └─ 보호 보존 필요: 도움닫기 또는 기본 이동으로 전환
└─ 보호 잔여 1개 이하: 도움닫기/슈퍼럭키/기본 이동 중 기대효율 비교
```

위 예시는 구조 설명용이며 90M에서 실제로 보호를 사용하는지는 성공 확률표와 전체 경로 최적화 결과로 결정한다.

보호를 `k`회까지 허용한 뒤 마지막에 무보호 기본 이동을 한다면, 동일 성공 확률 `p`를 가정할 때 해당 타일을 넘을 확률은 `1 - (1 - p)^(k + 1)`이다. 다만 보호와 음료수 소비량, 이후 타일의 위험, 도움닫기/슈퍼럭키 기회비용이 함께 달라지므로 단순 확률만으로 사용 횟수를 정하지 않고 전체 목표까지의 기대값을 비교한다.

구현 시에는 플랜별 고정 행동표만 두지 않고 `(플랜, 현재 위치, 보호/도움닫기/슈퍼럭키 잔량, 현재 타일 보호 실패 횟수)`를 상태로 하는 동적 정책을 사용한다. 같은 `P` 타일이라도 보호 4개를 보유하고 진입한 상태와 2개를 보유하고 진입한 상태는 이후 타일에 배분할 수 있는 보호 예산이 다르므로 별개의 후속 플랜을 가진다.

#### 사전 시뮬레이션과 실행 정책표

실행 중 모든 가능한 경로를 다시 탐색하면 불필요한 연산이 반복된다. 위치별 확률 데이터와 아이템 충전 규칙을 받은 뒤 다음 계산을 사전에 수행하여 플랜별 정책표를 생성한다.

1. 각 타일을 기본 이동으로 통과할 때의 실패 위험을 계산한다.
2. 보호를 `0~4개` 배정했을 때 해당 구간 통과 확률, 예상 음료수 소비량, 통과 후 예상 아이템 잔량을 계산한다.
3. 도움닫기과 슈퍼럭키로 해당 타일 또는 인접 위험 구간을 우회하는 경우와 비교한다.
4. 100M/200M/300M 플랜별로 보호를 집중할 후보 타일을 좁힌다.
5. 후보 타일마다 진입 시 보호 잔량과 연속 실패 횟수에 따른 후속 행동을 계산한다.
6. 목표 도달 확률과 음료수당 기대 보상을 기준으로 최종 정책표를 저장한다.

런타임에서는 먼저 현재 상태에 대응하는 정책표 항목을 조회한다. 다만 오프라인 계산 당시의 예상 상태와 실제 아이템 잔량이 다를 수 있으므로 연산을 완전히 제거하지 않는다. 정확히 일치하는 상태가 없으면 현재 위치 이후의 제한된 구간과 실제 아이템 잔량만 대상으로 후속 플랜을 재계산한다.

```text
정책 키
(플랜, 위치, 보호 잔량, 도움닫기 잔량, 슈퍼럭키 잔량, 현재 타일 보호 실패 횟수)
    ↓
권장 행동 + 성공 후 상태 키 + 실패 후 상태 키
```

정책표에 없는 상태가 발생한 경우에만 제한된 범위의 재계산을 수행하고, 계산할 수 없거나 데이터가 부족하면 안전 중지한다. 재계산 결과는 동일 실행 세션의 메모리 캐시에 저장하여 같은 상태에서 반복 계산하지 않는다. 이렇게 하면 복잡한 보호 분기와 실제 아이템 상태의 차이를 처리하면서도 실제 자동화 루프의 연산량과 판단 지연을 줄일 수 있다.

보호 정책은 다음 3단계로 실행한다.

1. **정확 조회:** 현재 위치와 모든 아이템 잔량이 일치하는 오프라인 정책 사용
2. **유사 골격 활용:** 같은 플랜/위치에서 가장 가까운 아이템 상태의 정책을 후보 골격으로 선택
3. **제한 재계산:** 실제 잔량으로 실행 불가능한 행동을 제거하고 현재 위치 이후만 다시 최적화

유사 정책의 행동을 검증 없이 그대로 실행하지 않는다. 예를 들어 보호 4개 기준 정책을 보호 2개 상태에서 조회했다면 보호 사용 예산과 실패 후 분기가 실제 잔량을 초과하는지 검사하고, 초과하는 경우 반드시 제한 재계산을 거친다.

시뮬레이션은 단순 무작위 반복만 사용하지 않고 상태 전이 확률을 이용한 동적 계획법을 우선한다. 규칙이 복잡해져 닫힌 형태로 계산하기 어려운 부분은 Monte Carlo 시뮬레이션으로 정책 후보를 비교하고, 고정된 난수 시드와 충분한 반복 횟수를 사용해 결과를 재현할 수 있게 한다.

#### 희소 확률 데이터와 루트 갱신

초기에는 모든 10M 구간의 확률이 제공되지 않는 것을 전제로 원본 데이터와 생성 결과를 분리한다.

- `event_config.json`: 이벤트 규칙과 데이터/정책 파일 경로
- `probability_data.json`: 확률이 확인된 타일만 저장하는 희소 원본 데이터
- `generated_policy.json`: 확률 원본으로부터 계산한 100M/200M/300M 정책 캐시

`probability_data.json`에는 모르는 타일을 임의의 `0%`나 평균값으로 채우지 않고 해당 키 자체를 두지 않는다. 각 타일은 성공 확률 외에 출처, 갱신 시각, 메모를 선택적으로 기록할 수 있다.

```json
{
  "schema_version": 1,
  "event_id": "2026_summer_event",
  "updated_at": null,
  "tiles": {
    "20": {
      "success_probability": 0.75,
      "source": "provided",
      "updated_at": "2026-08-03T00:00:00Z",
      "note": "확정 데이터"
    },
    "170": {
      "success_probability": 0.42
    }
  }
}
```

확률 데이터 로더는 알려진 타일만 정수 위치와 `0~1` 확률로 변환하고, 누락 타일 목록을 별도로 제공한다. 기본 정책인 `interpolate_bounded_linear`는 알려진 두 타일 사이의 누락 구간을 확률 흐름에 따라 선형 보간한다. 원본과 유추값을 구분하고 각 유추값에 양쪽 기준 타일을 기록한다.

- 알려진 두 타일 사이: 양쪽 확률 흐름으로 보간
- 가장 앞/뒤 기준점 바깥: 흐름을 확인할 양쪽 데이터가 없으므로 미확인 유지
- 원본 타일이 추가된 경우: 영향을 받는 보간 구간과 루트만 다시 생성
- 추후 실제 확률 흐름이 비선형으로 확인된 경우: 보간기만 교체하고 원본 파일 형식은 유지

확률값만 정규화해 SHA-256 지문을 생성하고 `generated_policy.json`에 `source_probability_fingerprint`로 저장한다. 이후 타일 하나가 추가되거나 확률이 수정되면 지문이 달라지므로 정책 캐시가 오래되었음을 판별하고 루트를 다시 생성한다. 출처나 메모만 수정한 경우에는 확률 계산 결과가 같으므로 불필요하게 루트를 재생성하지 않는다.

루트 생성기는 전체 정책 파일을 직접 수정하는 대신 항상 `probability_data.json`을 입력으로 받아 새로운 정책 캐시를 만든다. 따라서 갱신 순서는 다음으로 고정한다.

1. 새로 확인된 타일을 `probability_data.json`에 추가하거나 기존 확률을 수정한다.
2. 로더가 형식, 위치 단위, 확률 범위를 검증한다.
3. 현재 확률 지문과 정책 캐시의 원본 지문을 비교한다.
4. 지문이 다르면 영향을 받는 상태와 루트를 다시 계산한다.
5. 새 정책표와 데이터 커버리지/미확인 타일 목록을 저장한다.

#### 앱 기본 데이터와 개인 데이터

서버 수집·배포는 구현 범위에서 제외한다. 앱은 다음 두 데이터 계층만 서로 덮어쓰지 않고 분리해 관리한다.

1. **Bundled:** 앱 릴리즈에 포함된 기본 확률과 정책
2. **Personal:** 해당 사용자 환경에서만 수집·갱신되는 확률과 개인 정책

개인 데이터는 앱에 포함된 기본 파일을 직접 수정하지 않는다. 쓰기 가능한 실행 데이터 경로의 `event_data/2026_summer_event/personal_probability_data.json`에 별도로 저장하여 앱 업데이트 후에도 유지되게 한다. 최초 실행 시 개인 파일이 없으면 `personal_probability_data.template.json`을 기반으로 빈 파일을 만든다.

개인 데이터에는 타일별로 다음 통계를 누적한다.

- 기본/보호 이동 시도, 성공, 실패 횟수
- 도움닫기 시 실제 확률을 참조한 한 칸 뒤 타일의 시도/성공/실패 횟수
- 추정 성공 확률과 신뢰 수준
- 마지막 갱신 시각
- 화면 인식 신뢰도가 기준보다 낮아 제외한 표본 수

정책 입력을 만들 때 기본 우선순위는 `충분한 표본의 개인 데이터 > Bundled 원본 데이터 > 유추 데이터`로 한다. 개인 표본이 최소 기준을 충족하지 못하면 Bundled 값을 유지하고 개인 데이터는 참고 통계로만 보존한다. Bundled 데이터가 앱 업데이트로 바뀌어도 개인 원시 통계는 삭제하지 않고 새 기본값과 다시 결합해 개인 정책을 재생성한다.

모든 관측과 정책 갱신은 해당 사용자 장치 안에서만 처리하며 네트워크 전송 기능은 두지 않는다. 사용자는 설정에서 개인 데이터 사용을 끄거나 초기화할 수 있어야 하고, 초기화 전에는 확인 절차를 제공한다.

### 3.4 화면 인식 및 입력

- 이벤트 메인 화면 진입 여부 확인
- 현재 위치 또는 캐릭터가 선 타일 인식
- 아이템 스택 인식
- 기본 이동, 보호, 도움닫기, 슈퍼럭키 버튼 및 활성/비활성 상태 인식
- 이동 성공/실패, 보호 발동, 보상 획득 결과 인식
- 보상 팝업과 확인 버튼 처리
- 기존 `ADBController`와 `image_matcher`를 재사용
- 기준 환경은 현재 프로젝트와 동일한 `1280x720`, DPI `240`

숫자가 고정된 작은 범위라면 숫자별 템플릿 매칭을 우선 검토하고, 변동 범위가 크면 OCR 도입 여부를 별도로 결정한다.

### 3.5 이벤트 종료 처리

종료 화면은 현재 확보할 수 없으므로 초기 구현 범위에서 제외한다. 추후 제공되는 설정 종료 일시를 기준으로 종료를 판정한다.

종료가 확인되면 현재 동작을 안전하게 중단하고 상태를 `종료됨`으로 저장한다. 탭은 제거하지 않으며 실행 버튼을 비활성화하고 종료 안내와 최종 통계를 표시한다.

종료 시각과 기준 시간대는 코드 또는 설정 데이터로 분리하여 추후 값을 쉽게 교체할 수 있게 한다. 종료 화면 자료가 확보되면 화면 판정을 보조 수단으로 추가할 수 있다.

## 4. 필요한 추가 정보

### 4.1 정책 확정에 필수

1. **위치별 성공 확률표**
   - `0M`부터 마지막 판정 지점까지 각 10M 위치의 확률
   - `400M` 도달 시 처리 및 그 이후 이동 가능 여부
2. **목표 보상 획득 후 진행/초기화 규칙**
   - 100M/200M 플랜에서 목표 보상 획득 후 의도적으로 0M로 복귀하는 기능 또는 버튼이 있는지
   - 별도 복귀 기능이 없다면 실패할 때까지 전진하는 것이 실제 반복 방식인지
   - 400M 도달 시 자동으로 0M에서 새 시도가 시작되는지
3. **아이템 획득/초기화 규칙**
   - 시작 스택이 이벤트 최초 1회인지, 0M 롤백 또는 새 라운드마다 복구되는지
   - 추가 아이템을 얻는 위치/조건/확률
   - 최대 스택에서 추가 획득 시 처리 방식
4. **보상별 상대 가치(권장)**
   - 순서는 `100M < 200M < 300M < 350M`로 확정
   - 음료수당 기대 보상을 수치로 비교하려면 각 보상의 대략적인 상대 가중치 필요
5. **보호 시뮬레이션 결과 검증 기준(권장)**
   - 플랜별로 우선할 지표: 목표 도달 확률, 음료수당 보상 가치 또는 두 지표의 가중치
   - Monte Carlo 사용 시 허용 오차와 최소 반복 횟수

### 4.2 자동화 구현에 필수

1. 이벤트 메인 화면, 각 위치, 버튼, 성공/실패, 보상 팝업의 `1280x720` 스크린샷
2. 클릭해야 할 버튼 좌표 또는 이미지 템플릿
3. 이동/팝업 전환에 걸리는 대략적인 시간
4. 현재 위치와 아이템 스택이 화면에 항상 표시되는지 여부
5. 이벤트 시작/종료 일시와 기준 시간대
6. 네트워크 오류, 재접속, 일일 초기화 팝업 등 예외 화면 샘플

### 4.3 운영 설정으로 권장

- 최대 실행 시간 또는 최대 이동 시도 횟수
- 인식 실패 재시도 횟수
- 알 수 없는 화면에서 자동 중지할지 여부(기본값: 중지)
- 앱 재실행 후 이전 통계를 복구할지 여부

## 8. 현재 가정(확정 필요)

- `1칸 = 10M`이다.
- 도움닫기 성공 시 실제 위치는 `+30M`이며 성공률은 현재 위치 `-10M`의 값을 사용한다.
- 슈퍼럭키는 확률 판정 없이 `+30M` 이동한다.
- 일반 실패와 도움닫기 실패는 0M로 복귀한다.
- 보호 실패만 현재 위치를 유지한다.
- 일반 이동 또는 도움닫기 실패 후 새 시도가 시작되면 스킬은 보호 2개, 도움닫기 1개, 슈퍼럭키 2개로 복구된다.
- 보호는 성공과 실패 모두 1스택을 소비한다.
- 보호는 같은 타일에서 연속 사용할 수 있다.
- 보호 실패 직후 별도 팝업 없이 도움닫기 또는 슈퍼럭키로 전환할 수 있다.
- 스킬은 해당 버튼을 눌러 `Cancel` 선택 상태로 만든 뒤 `달리기` 버튼을 눌러 실행한다.
- 달리기와 도움닫기 실패는 즉시 결과 화면을 표시하고, 확인하면 0M의 새 시도로 복귀한다.
- 보호 실패는 결과 화면 없이 제자리에 머물며 보호 스택만 1개 감소한다.
- 행동 후 고정 대기시간을 사용하지 않고 현재 M 변화, 스택 변화 또는 결과창 출현을 반복 확인한다.
- 인식 불명확, 음료수 부족 또는 예외 화면은 기본 3회 재검증 후 오류를 기록하고 안전 중지한다.
- 이벤트 종료 시각은 `2026-08-27 12:00 (Asia/Seoul)`이다.
- 획득 보상은 위치 롤백과 무관하게 유지된다.
- 핵심 보상은 반복 획득할 수 있고, 이동 중 통과한 보상도 모두 획득한다.
- 350M 이후에는 남은 아이템을 최대한 사용하여 400M 도달을 목표로 한다.
- 음료수의 외부 충전 방식과 부족 상태는 자동화 정책의 범위에서 제외한다.
- 이벤트 종료 화면 인식은 초기 구현 범위에서 제외한다.
- 이벤트 종료 후에도 탭과 통계 조회는 가능하다.

위 가정은 실제 구현 전에 제공되는 게임 규칙 및 화면 자료로 확정한다.
