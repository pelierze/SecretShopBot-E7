# 자동 탐사 기능 계획 초안

- 작성일: 2026-09-24
- 상태: 네 직업 영입 및 일반·정예·보스 전투, 휴식·보급·상점 실행 연결 완료 / 등록 이벤트 진행 지원 / 최종 클리어 반복은 후속 검증
- 관련 이미지: `images/chaos/` (준비 중)

실기 검증: [그림자 로제 영입 검증 결과](knight-live-validation.md). 2026-09-24 단계별 확인에 이어 앱 `자동 탐사` 탭 통합을 완료했다. 실제 ADB 연결 및 시작 버튼을 통해 중간 수동 입력 없이 9회 입력, 약 24초 만에 그림자 로제 영입 완료까지 확인했다.

후속 실기 검증: [네 직업 영입 검증 결과](party-live-validation.md). 네 직업 UI와 공통 영입 흐름을 연결한 뒤, 시작 버튼 한 번으로 초기 화면부터 네 명 영입 완료까지 입력 27회, 71.52초에 성공했다.

## 1. 목적과 범위

낮은 단계의 난이도를 자동으로 반복하는 `자동 탐사` 기능을 추가한다. 한 회차는 영웅 선택, 노드 진행, 클리어(보스 처치)의 세 단계로 구성한다. 보스 클리어 후 처음으로 돌아가 다음 회차를 진행한다.

이 문서는 현재 확정된 흐름과 이후 보강할 내용을 구분한다. 정확한 난이도, 테마, 영웅 명단과 화면별 세부 조작은 후속 논의에서 확정한다. 이미지 파일명만으로 게임 규칙이나 영웅 구성을 확정하지 않는다.

## 2. 확정 요구사항

| 항목 | 내용 |
|---|---|
| 대상 | 낮은 단계 난이도의 탐사 반복 |
| 진행 단계 | 영웅 선택 → 노드 진행 → 클리어(보스 처치) |
| 테마 | 정해진 테마를 선택하여 진행 |
| 영웅 구성 | 그림자 로제 + 불사형 오공 + 데스티나 + 제뉴아 (직업별 1명) |
| 영웅 부재 | 필요한 영웅이 없으면 기능 중지 |
| 노드 종류 | 전투, 랜덤 이벤트, 정예 전투, 휴식, 상점, 보급, 보스 |
| 선택 우선순위 | 휴식 → 전투 → 정예 전투 → 상점 → 보급 → 랜덤 이벤트 |
| 보스 | 강제 진행 노드로, 일반 노드 우선순위에서 제외 |
| 클리어 이후 | 처음으로 돌아가 다음 회차 진행 |

## 3. 단계별 동작

### 3.1 영웅 선택 단계

1. 정해진 테마를 선택한다.
2. 지정 기사 1명(현재 그림자 로제)을 선택한다.
3. 지정한 커스텀 영웅 3명을 선택한다.
4. 필요한 영웅이 모두 선택되었는지 확인한다.
5. 구성이 완료되면 탐사에 진입하여 노드 진행 단계로 이동한다.

필요한 영웅 중 하나라도 없으면 기능을 중지한다. 다른 영웅으로 임의 대체하지 않는다.

보강할 내용:

- 정확한 난이도와 테마 이름
- 현재 지원 조합 외에 추가할 영웅의 이름·속성·선택 및 완료 이미지
- 커스텀 영웅 지정 방식과 배치 순서
- 영웅 검색·필터·스크롤 절차 및 선택 완료 판정
- 영웅 부재와 일시적인 인식 실패를 구분하는 기준
- 탐사 진입 전 추가 선택이나 확인 화면의 유무와 처리 방법

#### 3.1.1 테마 선택부터 영웅 선택 화면까지 (확인된 절차)

아래 이미지 경로는 `images/chaos/hero_selection/templates/themes/` 기준이다. 현재 준비된 파일의 경로를 유지한다.

| 순서 | 관측 및 행동 | 확인할 결과 |
|---|---|---|
| 1 | `start_chaos_button.png`를 탐색하여 클릭 | 다음 화면으로 전환되는지 확인 |
| 2 | 로딩을 기다림 | 테마 선택 메뉴 진입 |
| 3 | 신규 테마 해금 팝업의 `new_supply_open.png`가 보이면 화면을 클릭해 닫음 | 팝업이 사라지고 테마 선택 가능 |
| 4 | `select_supply_1.png`를 찾아 클릭 | `select_supply_2.png`로 변경됨 |
| 5 | 선택 상태 변경을 확인한 뒤 `select_theme_button.png` 클릭 | `select_heroes.png`가 나타남 |
| 6 | 영웅 선택 화면 진입 확인 | 직업별 영웅 영입 절차로 이동 |

신규 테마 해금 팝업은 조건부로 나타난다. 팝업이 없는 정상 흐름도 처리한다. 사용자가 설명한 팝업 닫기는 아무 곳이나 클릭하는 방식이며, 구현 시에는 팝업이 확인된 상태에서 일정한 화면 지점을 한 번 클릭하고 닫힘을 확인하는 방식을 제안한다. 실제 좌표는 전체 화면 자료를 확인한 뒤 정한다.

화면 전환 확인 방식 제안:

- 로딩은 고정 시간 경과만으로 완료 판정하지 않고, 다음 화면의 식별 이미지를 기다린다.
- 시작 버튼이 사라진 것만으로 테마 메뉴 진입을 확정하지 않는다. 해금 팝업 또는 테마 선택 이미지 등 다음 화면의 근거를 확인한다.
- 각 클릭 후에는 새 화면을 촬영하여 결과를 확인한다. 전환 대기 중 같은 버튼을 반복 클릭하지 않는다.
- 최대 대기 시간, 재인식 간격, 시간 초과 시 처리는 실제 로딩 자료를 기준으로 확정한다.

#### 3.1.2 직업별 영입 버튼 탐색 (방식 제안 / 확정 전)

영웅 선택 화면에는 기사, 전사, 정령사, 도적의 직업 심볼이 있고, 각 심볼 아래에 영웅 영입 버튼이 있다.

권장 방식은 **직업 심볼 인식 → 심볼 기준 아래쪽 영역 지정 → 영역 안에서 영입 버튼 인식 → 버튼 중심 클릭 → 영입 화면 전환 확인**이다.

- 절대 좌표 영역만 사용하는 방식도 고정된 화면에서는 가능하지만, 심볼을 기준점으로 삼으면 UI 위치가 조금 이동했을 때 대응하기 쉽다.
- 직업마다 기준 심볼과 상대 탐색 영역을 설정으로 관리한다. 영역은 해당 직업의 버튼만 포함하도록 전체 화면 자료에서 정한다.
- 네 직업의 영입 버튼 모양이 동일하면 공통 템플릿 한 개를 사용한다. 모양이 다른 경우에만 별도 템플릿을 둔다.
- 심볼이나 버튼이 불명확하거나 영역 안에서 버튼 후보가 여러 개 잡히면 임의 클릭하지 않고 재인식한다. 제한 초과 시 처리 기준은 구현 전에 정한다.
- 심볼을 찾지 못했다고 다른 직업 영역이나 전체 화면에서 같은 영입 버튼을 대신 클릭하지 않는다.
- 위치 기준점을 사용해도 화면 배율 변경까지 자동으로 해결되지는 않는다. 우선 기존 앱 기준 해상도를 유지한다.

추가로 필요한 자료: 네 직업과 버튼이 함께 보이는 전체 화면, 직업별 심볼 이미지, 영입 버튼 이미지, 버튼 클릭 후 나타나는 화면. 각 직업에 배정할 영웅과 영입 후 선택 완료 판정은 추가로 확정한다.

#### 3.1.3 제공된 영입권 화면 분석 (2026-09-24)

원본: [영입권 전체 화면](../../images/chaos/hero_selection/raw/Screenshot_2026.09.24_10.44.15.754.png). 제공된 ZIP에서 원본 PNG를 추출해 보관했다. 이미지 크기는 1280×720이며 DPI 설정은 이미지로 확인하지 않았다.

왼쪽부터 기사, 전사, 정령사, 도적 영입권 카드가 배치되어 있고, 각 카드 하단에 같은 모양의 `영웅 영입` 버튼이 있다. 아래쪽의 `돌아가기`, `탐사 입장` 버튼은 영입 버튼 탐색 영역에 포함하지 않는다. 이 화면의 `탐사 입장` 버튼은 비활성처럼 보이나, 활성 상태와의 비교로 확인이 필요하다.

다음 좌표는 제공 이미지에서 추정한 초기 탐색 범위이며, 구현 확정값이나 인식 검증 결과가 아니다. 좌표 원점은 이미지 왼쪽 위이며 영역은 `(x, y, 너비, 높이)`다.

| 직업 | 심볼 중심 근삿값 | 영입 버튼 탐색 영역 초안 | 버튼 중심 근삿값 |
|---|---|---|---|
| 기사 | `(220, 218)` | `(95, 470, 250, 90)` | `(220, 514)` |
| 전사 | `(500, 218)` | `(375, 470, 250, 90)` | `(500, 514)` |
| 정령사 | `(780, 218)` | `(655, 470, 250, 90)` | `(780, 514)` |
| 도적 | `(1060, 218)` | `(935, 470, 250, 90)` | `(1060, 514)` |

이 화면에서는 심볼 중심 `(cx, cy)`를 기준으로 대략 `(cx - 125, cy + 252, 250, 90)` 영역에서 공통 영입 버튼을 찾는 방식이 적합하다. 실제 상대 영역 값은 심볼 템플릿의 잘라내기 범위를 확정한 뒤 조정한다. 버튼 중심 근삿값은 위치 설명용이며, 실제 클릭은 해당 영역에서 인식된 버튼의 중심을 사용한다.

기사 영입 이후 화면은 아래 절에서 확인했다. 전사·정령사·도적의 실제 영입 완료 화면에서도 네 카드의 배치가 유지됨을 확인했다.

#### 3.1.4 속성 필터와 영웅 영입 (자료 확인 및 방식 제안)

사용자는 실행 전에 UI에서 영웅을 선택한다. 초기 지원 후보는 클래스당 1~3명이며, 선택한 영웅의 직업과 속성으로 목록을 좁힌 뒤 해당 영웅을 찾아 영입한다. 스크롤 탐색은 기본 절차에 포함하지 않는다. 현재 실제 대상은 기사 / 암속성 / 그림자 로제이며, 나머지 후보 명단과 이미지는 기사 영입이 정상 동작하는 것을 확인한 뒤 추가한다.

확인한 자료는 `images/chaos/hero_selection/` 아래에 있다.

| 자료 | 확인한 내용 |
|---|---|
| `raw/knight_full.png` | 기사 목록, 상단 필터 버튼, 선택 전 비활성처럼 보이는 영웅 영입 버튼 |
| `raw/knight_filter_menu.png` | 속성 5종과 전체 선택, 기사 직업 선택 상태, 영입 가능한 영웅만 보기 옵션 |
| `raw/knight_dark_filter.png` | 필터 메뉴가 닫힌 암속성 기사 목록에 그림자 로제가 표시됨 |
| `raw/knight_hero_selected_menu.png` | 그림자 로제 선택 테두리, 왼쪽 상세 정보, 활성 영웅 영입 버튼 |
| `raw/knight_select_finish.png` | 기사 카드가 그림자 로제와 영입 완료 표시로 교체됨. 다른 세 직업 카드 위치는 유지됨 |
| `templates/controls/hero_filter.png` | 필터 버튼 템플릿 준비됨 |
| `templates/controls/{fire,ice,forest,light,dark}_{1,2}.png` | 속성별 선택 전·후 템플릿 5쌍 준비됨. `_1`은 선택 전, `_2`는 선택 후 |
| `templates/heroes/knight_Shadow_Rose.png` | 목록에 표시되는 그림자 로제 초상화 일부 템플릿 준비됨 |

속성 아이콘 전체 화면 탐색에 대한 판단:

- 필터 메뉴가 열렸음을 확인한 상태에서는 전체 화면에서 목표 속성의 `_1` 또는 `_2`를 찾는 방식을 사용할 수 있다.
- 현재 작은 아이콘 템플릿은 필터 밖의 영웅 속성 표시와 유사하다. 필터 열림 판정 없이 전체 화면에서 검색·클릭하지 않는다. `hero_filter.png` 버튼은 닫힌 화면에도 있으므로 버튼 발견만으로 열림을 판정할 수 없다.
- 목표 `_2`가 이미 확인되면 다시 눌러 선택을 해제하지 않는다. `_1`을 누른 경우에는 새 화면에서 같은 위치 주변에 `_2`가 나타났는지 확인한다. 전·후 템플릿의 크기가 다를 수 있으므로 좌상단의 완전 일치 대신 중심 위치의 허용 오차를 사용한다.
- 속성은 다중 선택할 수 있으며 다음 직업 선택 시 필터가 초기화된다. 필터 메뉴 바깥을 클릭하면 닫힌다. 정상적인 새 직업 진입에서는 초기화된 상태에서 목표 속성만 선택한다. 같은 직업에서 재시도하는 경우에는 현재 선택 상태를 다시 확인한다.
- 선택 상태가 모호하거나 목표 후보가 여러 개면 클릭을 보류하고 재인식한다. 임계값을 낮춰 임의 클릭하지 않는다.

제공된 원본 5장에 현재 앱과 같은 컬러 `TM_CCOEFF_NORMED` 매칭을 적용한 참고 결과:

- 필터 메뉴 화면에서 속성 `_1` 5종은 모두 유사도 1.000으로 해당 아이콘에 매칭됨.
- 필터가 닫힌 `knight_full.png`에서도 `fire_1` 0.863, `forest_1` 0.869, `ice_1` 0.911로 영웅 목록의 속성 표시가 잡힘. 기존 기본 임계값 0.8만으로 화면을 구분할 수 없음.
- 그림자 로제 템플릿은 암속성 목록에서 1.000, 선택 후 목록에서 0.976으로 매칭됨. 선택 테두리가 생긴 이후에도 인식 가능한 것으로 확인됨.
- 선택된 속성의 필터 메뉴 전체 화면은 이번 자료에 없으므로 `_2` 상태 전이의 실제 성공 여부는 아직 검증하지 않음. 위 수치는 제공 스크린샷에 대한 결과이며 실시간 인식 보장은 아님.

영입 흐름 초안은 `직업 영입 → 필터 열림 확인 → 목표 속성 선택 및 상태 확인 → 필터 닫힘 확인 → 지정 영웅 선택 → 선택 상태 확인 → 활성 영웅 영입 버튼 클릭 → 해당 직업 카드의 영입 완료 확인`이다. 완료 카드는 원래 큰 직업 심볼과 영입 버튼이 사라지므로, 이 심볼을 완료 확인에 재사용하지 않는다.

사용자는 그림자 로제가 설명용 예시가 아닌 실제 사용할 기사임을 확인했다. 따라서 초기의 배포 기사 고정 요구는 현재 지정 기사(그림자 로제)를 사용하는 계획으로 갱신한다. 영입 후 상단 수치가 `0/12`에서 `2/12`로 변하는 것은 관측 사실로만 기록하며, 해당 수치의 규칙은 아직 확정하지 않는다. 미보유 상태 표시도 추가 검증 항목으로 남긴다.

#### 3.1.5 기사 1명 우선 검증 범위 (완료된 1차 검증 기록)

현재 목표는 기존에 저장한 이미지로 그림자 로제를 인식하고 영입하는 단계까지 확인하는 것이다. 다른 직업 후보 등록과 자동 탐사 전체 구현은 이 확인 이후로 미룬다.

확정한 정상 흐름:

1. 기사 영입권에서 영입 버튼을 눌러 기사 목록으로 진입한다.
2. `hero_filter.png`로 필터를 열고 메뉴가 실제로 나타났는지 확인한다.
3. 화면 전체에서 `dark_1.png`를 찾아 클릭하고 같은 위치 주변에서 `dark_2.png`로 변경됐는지 확인한다. 이미 `dark_2`이면 다시 누르지 않는다.
4. 필터 메뉴 밖에서 영웅 카드나 영입 버튼이 없는 배경을 클릭하고 메뉴가 닫혔는지 확인한다. 제공된 1280×720 화면에서는 `(960, 590)` 근처가 후보이며, 실제 실행 전에 확인한다.
5. `knight_Shadow_Rose.png`를 찾아 목록의 그림자 로제를 선택한다.
6. 선택 상태를 확인한 뒤 활성화된 영웅 영입 버튼을 클릭한다.
7. 기사 카드의 영입 완료를 확인하고 이 검증 실행을 종료한다. 다른 직업이나 탐사 입장으로 자동 진행하지 않는다.

기존 `ImageMatcher.find_image`를 그대로 사용한 저장 이미지 검증 결과:

- 템플릿: `templates/heroes/knight_Shadow_Rose.png`, 141×44 픽셀. 경로·파일명·이미지 수정 없이 읽힘.
- 임시 검증 임계값 0.90에서 암속성 목록과 선택 후 목록 2장을 모두 인식함. 매칭 영역은 두 화면 모두 `(491, 296, 141, 44)`.
- 나머지 원본 4장에서는 검출되지 않음. 최대 유사도는 0.485 이하. 여기에는 영입 완료 카드의 다른 크기 초상화도 포함되므로 목록용 템플릿을 완료 판정에 재사용하지 않는다.
- 6장 검사는 저장 방식과 목록 내 영웅 인식의 적합성을 확인한 결과다. 실제 클릭, 로딩 대기, 필터 선택 후 상태 전이, 최종 영입 성공을 실행 검증한 것은 아니다. 0.90도 최종 운영 임계값으로 확정하지 않는다.

별도 영웅 후보 자료 추가 없이 이 기사 흐름을 먼저 준비한다. 필터 열림, 영웅 선택 상태, 활성 영입 버튼, 영입 완료 판정에 사용할 영역은 제공 원본에서 정할 수 있다. 선택된 속성 필터 화면과 실제 전환 타이밍은 실행 중 확인해야 한다.

### 3.2 노드 진행 단계

자료 준비 공간: `images/chaos/node_progression/`. [노드 이미지 및 금지 선택지 준비 안내](../../images/chaos/node_progression/README.md)에 저장 위치와 예외 처리 설계를 기록한다. `exploration.py`, `node_observer.py`, `node_layout.json`으로 일반·정예·보스 전투, 휴식·보급·상점과 공통 금지 이미지 검사를 GUI에 연결했다. 미지원 노드가 선택 대상이 되면 우선순위를 무시하고 다른 경로로 우회하지 않고 진입 전에 중지한다.

사용자 확정 규칙: 탐사 중 선택지를 고르는 모든 상황에서 최신 전체 화면의 금지 이미지 스캔을 최우선으로 수행한다. 특정 이벤트·노드에 한정하지 않고 공통 목록을 검사하며, 같은 이미지가 여러 곳에 나타나면 모든 위치를 수집한다. 해당 항목을 후보에서 먼저 제외한 후 허용 후보에만 우선순위를 적용한다. 노드 내부 선택지는 이벤트별 규칙을 별도로 정한다. 보급의 전리품 선택 화면에서는 금지 항목을 제외한 모든 전리품을 허용하며, 그 외 미등록 선택 화면에서는 금지 이미지 미검출만으로 항목을 선택하지 않는다. 모든 후보가 금지되거나 판단이 모호하면 클릭하지 않고 재인식 후 중지하며 화면과 사유를 남긴다. 구체적인 인식 영역과 대체 선택 규칙은 전체 화면 자료를 확인한 뒤 확정한다.

제공된 금지 이미지는 `dont_select_1.png`(석판: 꼬리 달린 별의 예언), `dont_select_2.png`(별의 서)이다. 노드 아이콘 7종과 함께 파일 읽기·내용을 확인했으며 실제 화면 매칭은 검증 전이다. 추가된 `supply_node.png`는 보급 노드이며 사용자 지정에 따라 상점 다음, 랜덤 이벤트 이전으로 배치한다.

1. 현재 진입 가능한 노드를 확인한다.
2. 강제 보스 진행 상황이면 클리어 단계로 이동한다.
3. 일반 노드 선택 상황이면 진입 가능한 후보에 아래 우선순위를 적용한다.
4. 선택한 노드에 진입하고 해당 노드의 절차를 수행한다.
5. 노드 완료 후 다음 선택 화면으로 돌아가 같은 판단을 반복한다.

| 우선순위 | 노드 | 세부 절차 상태 |
|---|---|---|
| 1 | 휴식 | 랭크업: 오공 우선, 오공 랭크 5이면 제뉴아 |
| 2 | 전투 | 전투 시작, 진행, 종료 후 절차 보강 필요 |
| 3 | 정예 전투 | 일반 전투와 같은 절차 사용 (실행 연결 완료) |
| 4 | 상점 | 구매 없이 퇴장 (실행 연결 완료) |
| 5 | 보급 | 영웅 영입 대신 전리품 선택, 금지 전리품 제외 (실행 연결 완료) |
| 6 | 랜덤 이벤트 | 랭크업·전투 우선, 무작위 전리품 후순위. 등록 이벤트만 실행 |
| 적용하지 않음 | 보스 | 강제 진행, 전투는 일반 전투와 동일. 처치 후 클리어 확인은 별도 |

보강할 내용:

- 같은 종류는 위쪽부터, 같은 높이는 왼쪽부터 선택 (초기 구현 기본값)
- 진입 가능한 노드와 잠겨 있거나 연결되지 않은 노드의 구분
- 전투 정체 판정 시간·자동 전투 켜짐 확인 기준과 패배 시 처리
- 보급품·강화·보상 등 추가 화면이 나타나는 위치와 처리 규칙
- 노드 선택 후 실제 진입 및 완료를 확인할 화면 기준

#### 3.2.1 전투 정체와 스토리 공통 처리

사용자 요구사항: 전투가 진행되지 않으면 자동 전투 옵션을 켠다. 탐사 도중 스토리가 나타나면 건너뛰기 후 확인 버튼을 누른다.

자동 전투 버튼은 활성화 시 회전하므로 켜짐/꺼짐 이미지 비교 대신 첫 전투의 진행 여부로 초기 검증한다. 첫 전투에서 턴·체력 등 진행 신호가 일정 시간 유지되면 한 번만 눌러 켜고 실제 진행을 확인한다. 이미 전투가 진행 중이면 누르지 않는다. 검증 완료 후 다음 전투에서는 자동 전투 설정이 유지된다는 사용자 설명에 따라 다시 토글하지 않는다. 진행이 재개되지 않아도 반복 토글하지 않고 중지한다. 연출·로딩·스토리 대기를 전투 정체로 오인하지 않도록 정체 판정 시간과 관측 기준은 추가 검증 후 확정한다.

스토리는 건너뛰기 버튼 클릭 후 해당 확인 팝업이 나타났는지 확인하고, 팝업 내부의 확인 버튼을 누른다. 팝업이 닫히면 최신 화면으로 진행 상태를 다시 판별한다. 다른 종류의 확인 팝업에는 이 절차를 적용하지 않으며, 선택지 판단 시 공통 금지 이미지 우선 검사를 유지한다.

스토리의 건너뛰기 버튼은 화면 터치 후 표시되며, 터치 전 공통 UI는 없다는 사용자 설명을 반영한다. 초기 스토리는 이미 진행하여 터치 전 원본을 지금 확보할 수 없다. 제공된 버튼 표시 화면 1장과 기존 자료에서 확인한 서로 다른 배경의 확인 팝업 2장으로 표시 이후 흐름을 먼저 준비한다. 버튼을 드러내는 최초 터치는 아직 검증하지 않았으며, 미인식 화면에 임의 터치하는 동작을 활성화하지 않는다. 다음 스토리 발생 시 터치 전 화면·좌표·표시 전환을 확인하고 연결한다.

이미지는 `images/chaos/node_progression/templates/battle/`, `templates/story/`에, 전체 원본은 같은 단계 폴더의 `raw/battle/`, `raw/story/`에 준비한다. 자동 전투 전후 자료는 실기 중 확보했고, 제공된 스토리 버튼·확인 팝업을 인식하도록 연결했다. 버튼 숨김 상태의 최초 터치와 다양한 장면 검증은 남아 있다.

#### 3.2.2 휴식 랭크업

사용자 확정 규칙: 휴식에서는 영웅 랭크업을 진행한다. 불사형 오공을 우선 선택하고, 오공이 랭크 5여서 더 올릴 수 없으면 제뉴아를 선택한다. 일반 영웅 레벨 60과 탐사 내 랭크를 구분한다. 오공 부재나 인식 실패를 랭크 5로 간주하지 않는다. 두 영웅 모두 랭크업 불가일 때의 대체 행동은 아직 미정이다.

실기에서 휴식 → 영웅의 랭크를 올린다 → 오공 선택 → 영웅 랭크업 → 오공 랭크 1에서 2로 변경 확인 → 결과 닫기 → 떠나기 → 지도 복귀까지 확인했다. 이후 새 실행 코드로 오공 2에서 3까지 자동 진행했다. 세부 기록은 [노드 진행 실기 검증](node-live-validation.md)을 참조한다. GUI는 `ExplorationBot`으로 연결됐다.

#### 3.2.3 정예·보스·보급·상점 규칙 (2026-09-25 확정)

아래 노드는 실행 코드와 GUI에 연결했다. 일반·정예·보스 전투 및 보급은 실기 검증했고, 상점은 제공된 전체 화면 재생으로 구매 없이 퇴장을 검증했다. 총 3층이며 모든 층의 노드 절차는 동일하다(사용자 확인). 마지막 층 클리어 화면과 다음 회차 연결은 별도로 검증한다.

- **정예·보스:** 사용자 설명에 따라 진입 → 전투 준비 → 시작 → 자동 전투 진행 → 승리 처리의 공통 절차를 재사용한다. 자동 전투 초기 검증 결과도 노드 종류별로 초기화하지 않고 유지한다. 노드 종류에 따라 상세 화면의 제목·아이콘은 별도로 식별한다. 보스 승리를 일반 노드 복귀로 가정하지 않고 처치 후 결과·클리어 화면을 확인한다.
- **보급:** 영웅 영입과 전리품 선택 중 전리품 경로를 택한다. 매 선택 시 금지 이미지를 먼저 전체 화면에서 검사한 뒤 전리품 카드 영역에 연결하여 해당 카드만 제외한다. 나머지 전리품은 종류별 허용 목록 없이 선택할 수 있다. 재현 가능한 초기 기본값으로 화면 위쪽부터, 같은 높이는 왼쪽부터 고른다. 전리품 선택 화면과 카드가 확인된 경우에만 이 규칙을 적용하며, 다른 미등록 선택 화면으로 확대하지 않는다. 선택 후 확인 단계와 수령·지도 복귀를 확인한다. 전부 금지이거나 금지 항목과 카드의 연결이 불명확하면 입력 없이 중지한다. 임의로 영웅 영입으로 대체하지 않는다.
- **상점:** 상품·구매·새로고침을 누르지 않고 해당 상점의 떠나기/닫기 버튼으로 퇴장한다. 퇴장 확인 팝업이 실제로 있을 때만 식별 후 처리하고 지도 복귀를 확인한다. 구매 정책은 후속 수정 대상으로 남긴다.

노드 우선순위는 휴식 → 전투 → 정예 전투 → 상점 → 보급 → 랜덤 이벤트로 유지하며 보스는 강제 진행으로 분리한다. 랜덤 이벤트는 영웅 이탈과 전체 생명력 감소 등 기존 파티에 손실을 주는 선택지를 배제한다. 랭크업과 전투를 우선하고 무작위 전리품은 다른 허용 대안이 없을 때 후순위로 선택한다. 확인된 결과만 이미지와 연결하고, 미등록 이벤트는 선택 없이 중지한다.

필요한 화면: 정예·보스 상세/준비 화면과 보스 승리 이후 화면, 보급 최초 선택 화면/전리품 카드 목록/선택 및 수령 후 화면, 상점 전체 화면/퇴장 후 화면. 기존 전체 원본에 해당 자료가 있으면 재사용하며, 이미지가 부족한 경우에만 추가 확보한다.

### 3.3 클리어(보스 처치) 단계

1. 강제 보스 노드에 진입한다.
2. 보스 전투를 진행한다.
3. 보스 처치와 탐사 클리어를 확인한다.
4. 클리어 후 나타나는 화면을 처리하고 처음으로 복귀한다.
5. 영웅 선택 단계부터 다음 회차를 진행한다.

보강할 내용:

- 일반 전투 승리와 보스 클리어를 구분하는 기준
- 보스 전투는 일반 전투 절차를 재사용하되 상세·준비 화면의 식별 이미지 확인
- 결과·보상 화면의 순서와 버튼
- 처음으로 복귀했음을 확인하는 화면
- 다음 회차에서 테마·영웅 선택이 유지되는지 여부
- 보스 패배 및 재도전 처리
- 반복 횟수 제한 등 추가 종료 조건의 필요 여부

## 4. 전체 흐름

```text
시작
  ↓
영웅 선택: 테마 → 지정 기사 1명(현재 그림자 로제) → 커스텀 영웅 3명
  ├─ 필요한 영웅 없음 → 중지
  ↓ 구성 완료
노드 진행: 진입 가능한 후보 확인
  ├─ 일반 노드 → 우선순위로 선택 → 노드별 절차 → 노드 진행 반복
  └─ 강제 보스 → 보스 전투 → 클리어 확인
                                 ↓
                         결과 처리 및 처음으로 복귀
                                 ↓
                         다음 회차 영웅 선택
```

패배, 인식 실패, 예상하지 못한 화면의 처리 방식은 아직 확정하지 않았다.

## 5. 구현 방향 제안

아래 항목은 확정 요구사항이 아닌 구현 제안이며, 세부 절차 보강 시 조정한다.

- 화면 인식, 다음 행동 판단, 입력 실행을 분리하여 단계별로 검증한다.
- 버튼 입력 후 실제 화면 전환을 확인한 다음 상태를 변경한다.
- 현재 단계, 선택한 노드, 클리어 횟수와 중지 사유를 기록한다.
- 사용자 중지를 각 단계와 대기 구간에서 처리한다.
- 화면이 불명확하면 제한적으로 재인식한 뒤 중지한다. 재시도 횟수와 대기 시간은 화면 자료 확인 후 정한다.
- 기존 앱플레이어 세션 관리와 이미지 인식·ADB 입력 구조의 재사용 범위를 구현 전에 확인한다.

현재 GUI는 세션별 `자동 탐사` 탭으로 제공한다. `src/chaos/bot.py`의 `PartyRecruitmentBot`은 네 직업의 순차 영입과 중지·대기를 담당하고, `observer.py`의 `RecruitmentObserver`는 화면 인식, `theme_selection.py`는 고용 서약서 선택 상태 판정을 담당한다. 기존 기사 설정은 `recruitment_layout.json`으로 확장했으며 직업, 영웅 후보, 이미지 경로, 원본 영역, 탐색 영역과 대기 설정을 함께 관리한다. `KnightRecruitmentBot`과 `KnightObserver`는 기사 단독 회귀 검증용으로 유지한다.

## 6. 이미지 준비와 연결

`images/chaos/`를 관련 이미지 준비 경로로 사용한다. 현재 파일은 준비 중인 자료로 취급하고, 화면과 용도를 확인한 뒤 인식 대상으로 연결한다.

영웅 선택 단계 전용 준비 공간은 `images/chaos/hero_selection/`이다. 원본 화면은 `raw/`, 인식용 이미지는 `templates/` 아래에 용도별로 보관한다. 파일 이름, 준비할 화면, 이미지 목록과 교체 절차는 [영웅 선택 이미지 준비 안내](../../images/chaos/hero_selection/README.md)에 기록한다.

| 단계 | 확인할 이미지·화면 |
|---|---|
| 영웅 선택 | 테마, 난이도, 영웅 목록·필터, 각 영웅, 선택 완료, 탐사 진입 |
| 노드 진행 | 각 노드 유형, 진입 가능 표시, 노드 진입 버튼, 노드별 내부 화면과 완료 화면 |
| 클리어 | 보스 식별, 전투 결과, 탐사 클리어, 결과·보상 처리, 시작 화면 복귀 |
| 공통 | 로딩, 확인 팝업, 패배, 진행 불가 및 인식 실패 사례 |

이미지별로 실제 파일명, 화면상의 의미, 인식 영역, 클릭 대상 여부, 입력 후 기대 화면을 기록한다. 이미 있는 파일의 이름이나 내용을 이 초안 작성 과정에서 변경하지 않는다.

## 7. 단계별 작업 계획

| 순서 | 작업 | 완료 기준 | 상태 |
|---|---|---|---|
| 1 | 요구사항 초안 작성 | 세 단계, 영웅 부재 중지, 노드 우선순위, 반복 흐름 정리 | 초안 작성 완료 |
| 2 | 세부 절차와 이미지 매핑 보강 | 테마·영웅 명단 및 각 화면의 진입·행동·완료 기준 확정 | 예정 |
| 3 | 영웅 선택 단계 구현 | 정상 구성으로 탐사 진입, 필요한 영웅 부재 시 중지 검증 | 네 직업 영입과 탐사 입장 연결 완료 |
| 4 | 노드 진행 단계 구현 | 후보 인식, 우선순위 선택, 각 노드 내부 절차와 복귀 검증 | 일반·정예·보스·휴식·보급·상점 연결 완료, 이벤트별 추가 등록 진행 |
| 5 | 클리어 단계 구현 | 보스 클리어 판정, 결과 처리, 처음으로 복귀 검증 | 예정 |
| 6 | 반복 실행 및 GUI 통합 | 다음 회차 연결, 사용자 중지, 상태 표시와 로그 검증 | 네 직업 GUI·중지·로그 완료, 반복 실행은 예정 |

각 구현 단계는 해당 화면의 세부 규칙과 이미지 매핑이 정리된 뒤 진행한다.

## 8. 향후 검증 항목

- 지정 기사 1명과 커스텀 영웅 3명이 정확히 선택되는가?
- 필요한 영웅이 없을 때 임의 대체나 탐사 진입 없이 중지하는가?
- 진입 가능한 후보에만 `휴식 → 전투 → 정예 전투 → 상점 → 보급 → 랜덤 이벤트` 순위를 적용하는가?
- 강제 보스 진행을 일반 노드 우선순위와 별도로 처리하는가?
- 각 노드의 절차 완료를 확인한 뒤 다음 노드를 선택하는가?
- 일반 전투 승리를 탐사 클리어로 잘못 판단하지 않는가?
- 보스 클리어 후 처음으로 복귀하여 다음 회차를 시작하는가?
- 사용자 중지와 추후 확정할 예외 처리 규칙이 각 단계에서 동작하는가?

## 9. 다음 보강 순서

현재 네 영웅 영입과 일반·정예·보스·휴식·보급·상점의 GUI 연결을 완료했다. 확인된 이벤트는 랭크업·전투 우선으로 연결했으며, 마지막 층 클리어 후 반복 연결은 후속 구현 범위다. 실기 및 저장 화면 검증 범위는 node-extension-validation.md에 기록한다.

추가 영웅 후보가 필요하면 파일별 게임 내 이름·속성, 필터 적용 후 목록 화면, 선택 직후 상세 정보 화면, 영입 완료 카드 화면을 준비한다. 현재 파일만 있는 `soul_weaver_Fenne.png`, `thief_dark_karin.png`, `thief_Rhianna and Luciella.png`는 아직 후보로 등록하지 않았다.

현재 등록된 네 후보에 대해서는 추가 이미지가 필요하지 않다. 필터 버튼과 속성 아이콘은 공통으로 재사용하고, 파일명은 유지한 채 `recruitment_layout.json`에 명시적으로 연결한다. 후보 중 하나를 사용자가 UI에서 선택하며, 찾지 못한 영웅을 임의 대체하지 않는다.

## 패배 후 재시작 (2026-09-25)

패배 → 결과 정산 → 초기 화면 복귀를 확인한 후 동일한 영웅 설정으로 새 회차를 시작한다. 사용자 중지는 회차 전환 중에도 유지한다. 날짜 변경 안내는 범위에서 제외하며 알 수 없는 화면에서는 중지한다. [실패 재시작 및 우선순위 회귀 검증](failure-restart-validation.md) 참조.
